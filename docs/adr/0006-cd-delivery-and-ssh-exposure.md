# ADR-0006: 배포 전달 방식과 22번 포트 노출

- 상태: 채택
- 날짜: 2026-08-30

## 상황
세션 6에서는 서버에 직접 들어가 손으로 배포했다. Phase 0의 DoD는 "git push 하면 실제 URL에 반영된다"이고,
사람이 빠져야 그게 성립한다. 결정할 것이 둘이다.

1. 코드가 **어떤 경로로** 서버에 도착하는가
2. GitHub 러너가 **어떻게** 서버에 들어가는가 — 러너는 매번 새 VM이고 IP가 고정되지 않는다

## 결정 1 — 코드 전달: 서버에서 `git fetch` + 서버에서 빌드

후보
1. ssh → 서버가 git fetch → 서버에서 `docker compose up --build`
2. CI에서 이미지 빌드 → GHCR push → 서버는 pull만
3. rsync/scp로 파일 전송 → 서버에서 빌드

**1번.**

- 부품이 하나도 늘지 않는다. 2번은 레지스트리 + 인증 + 이미지 수명 관리가 따라온다 (R3)
- 세션 6에서 t3.micro 빌드 33초를 이미 확인했다. 감당 못 할 부하가 아니다
- 3번은 서버가 "지금 어느 커밋인지"를 잃는다. git이면 `git rev-parse HEAD` 한 줄이 답이다

`git pull`이 아니라 **`git reset --hard <이번 커밋 SHA>`**를 쓴다. pull은 *실행 시점*의 origin/main을
가져오므로, 배포가 밀리는 사이 다음 커밋이 올라오면 테스트를 통과한 커밋과 서버에 뜬 커밋이 어긋난다.
SHA를 박아야 "이 초록불이 이 코드"가 성립한다. `.env`는 추적 대상이 아니라 reset이 지우지 않는다.

**뒤집는 조건**: 서버 빌드가 메모리를 넘거나(OOM) 배포 시간이 앱 응답에 보이기 시작하면 2번으로.
그때 "롤백이 태그 하나"라는 이득이 같이 따라온다.

## 결정 2 — 22번 포트: 상시 개방(0.0.0.0/0) + 키 인증만

세 후보 모두 "러너 IP가 고정되지 않는다"는 같은 문제를 푼다.

| # | 방식 | 얻는 것 | 치르는 것 |
|---|------|---------|-----------|
| 1 | 22번을 0.0.0.0/0으로 상시 개방 | secret 2개로 끝. 추가 부품 0 | sshd가 인터넷에 노출. 스캔·무차별 시도 로그가 상시로 쌓인다 |
| 2 | Actions IP 대역만 허용 | 노출면 축소 | `api.github.com/meta`의 대역이 수천 개. 보안그룹 규칙 상한(기본 60)을 한참 넘는다 — **실행 불가** |
| 3 | 배포할 때만 열고 닫기 | 상시 노출 0 | AWS IAM 키를 GitHub에 추가(secret 2개 더) + `ec2:AuthorizeSecurityGroupIngress` 권한. job이 중간에 죽으면 규칙이 열린 채 남는다 |

**1번.** 2번은 규칙 개수 때문에 애초에 성립하지 않는다. 1번과 3번 사이는 실제 위험 차이로 갈랐다 —
비밀번호 인증이 꺼져 있고(Ubuntu AMI 기본) 키 인증만 받는 sshd에서, 개방으로 늘어나는 위험은
"실패한 로그인 시도가 로그에 쌓인다"에 가깝다. 3번이 없애는 것은 그 로그이고, 대신 들여오는 것은
**서버 방화벽을 조작할 수 있는 IAM 자격증명이 GitHub에 상주하는 상태**다. 지금 단계에선 후자가 더 크다 (R3).
러너 → EC2 키는 로컬 접속용 `.pem`과 분리한 전용 키다. 유출 시 그 키만 `authorized_keys`에서 지우면 끝난다.

호스트 키는 매 배포마다 `ssh-keyscan`으로 새로 받는다(TOFU). 러너가 새 VM이라 known_hosts가 비어 있기
때문이다. 이 구간에서 새는 비밀은 없다 — SSH 공개키 인증은 개인키를 전송하지 않는다. 다만 공격자가
가짜 서버로 유도해 "배포 성공"을 위조하는 것까지는 막지 못한다.

## 뒤집는 조건
- 서버에 실제 사용자 데이터가 들어가면 3번으로 올린다 (ROADMAP 6장 백로그)
- 인스턴스 IP가 고정(Elastic IP)되면 호스트 키를 secret으로 박아 TOFU를 없앤다
- 인스턴스를 재생성하면 `EC2_HOST` secret과 서버의 `authorized_keys`를 다시 세팅해야 한다
