# ADR-0005: 서버 조립도 분리와 DB 위치 전환 경로

- 상태: 채택
- 날짜: 2026-08-30

## 상황
서버(EC2)에서 도는 구성은 로컬과 두 가지가 다르다. Nginx가 앞에 서고, DB가 컨테이너가 아니라 RDS다.
게다가 RDS는 오래 켜둘 수 없다 — 신규 AWS 계정은 12개월 프리티어가 아니라 크레딧 차감 방식이라
검증이 끝나면 지우고 DB를 서버 안으로 내려야 한다 (R3: 운영 인력 0명, 비용도 0에 가깝게).

즉 "서버 구성"이 한 번 정해지고 끝나는 게 아니라, **DB 위치가 도중에 바뀐다.**

## 후보
1. `docker-compose.yml` 하나에 프로필로 로컬/서버를 모두 표현
2. `docker-compose.yml`(서버 모양) + 자동 적용되는 `docker-compose.override.yml`(로컬)
3. `docker-compose.prod.yml` 별도 파일

## 결정과 근거
**3번.** 그리고 prod 파일 안에서 postgres만 `profiles: ["localdb"]`로 잠근다.

- 서버에서 무엇이 도는지 파일 하나를 열면 다 보인다. 2번은 로컬에서 자동 적용되는 파일이 있다는 걸
  모르면 서버에서 `-f`를 빠뜨려 조용히 틀린다 — 1인 운영에서 조용한 실패가 가장 비싸다 (R3)
- api는 DB가 어디 있는지 모른다. `.env`의 `DATABASE_URL`만 본다. 세션 4에서 이미 세운 메커니즘을
  그대로 재사용한다. RDS → 컨테이너 전환이 **파일 수정이 아니라 `.env` 한 줄 + 프로필 플래그**로 끝난다
- ADR-3(PostgreSQL + PGVector)의 "뒤집는 조건"이 문서 속 문장이 아니라 실행 가능한 경로로 존재한다
- 대가: api·redis·nginx 정의가 두 파일에 중복된다. 서비스 3개 규모에서는 중복보다 명시성이 싸다

Nginx는 `proxy_buffering off`로 둔다 (ADR-8). 로컬에서 3청크 스트리밍으로 재보니 버퍼링을 켜도
지연이 없었다 — 청크가 작으면 그냥 통과한다. 다만 Phase 1의 토큰 스트림처럼 양이 늘면 갇히고,
이 트래픽 규모에서 버퍼링으로 얻을 게 없으므로 끈 채로 간다. 근거 없는 부적이 되지 않도록
Phase 1에서 실제 SSE로 다시 측정한다.

## 뒤집는 조건
- 서비스가 5개를 넘어 두 파일의 중복이 실제로 어긋나기 시작하면 2번(override 패턴)으로 옮긴다
- 트래픽이 늘어 정적 응답 캐싱이 필요해지면 `proxy_buffering`을 경로별로 나눈다
