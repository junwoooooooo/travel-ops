# ADR-0010: 외부 API는 한 통로로 나가고, 실패의 무게는 호출자가 정한다

- 상태: 채택
- 날짜: 2026-09-01

## 상황
세션 9까지 이 앱이 바깥으로 내는 커넥션은 asyncpg의 DB 하나뿐이었다. 세션 12~14의 planning
그래프는 실존하는 장소(`place_id`)와 날씨를 입력으로 받는데, 그 입력을 만드는 층이 통째로
비어 있다. Redis는 컨테이너·볼륨·`depends_on`까지 서 있지만 패키지도 설정 통로도 코드도 없다.

외부 API는 DB와 다른 종류의 부품이다. **우리가 고칠 수 없고, 느리고, 예고 없이 죽고, 부를
때마다 돈이나 쿼터를 쓴다.** 지금 이 층의 규약을 정하지 않으면 세션 12~14에서 그래프 노드마다
`httpx.get`이 흩어지고, 타임아웃·재시도·캐시가 노드 수만큼 복제된다.

ROADMAP은 이 세션의 목표를 한 줄로 적어 두었다: **"장애 격리: 날씨 API 죽어도 일정은 나옴".**
그 문장이 무슨 뜻인지가 이 문서의 주제다.

## 후보
외부 API 실패를 어떻게 다룰 것인가에 대해:
1. 모든 외부 호출을 같은 방식으로 감싼다 — 실패하면 예외, 호출자가 각자 try/except
2. 모든 외부 호출을 같은 방식으로 감싼다 — 실패하면 `None`, 호출자가 각자 None 검사
3. 통로는 하나로 두되, **무엇이 치명적인지는 각 API 모듈이 자기 자리에서 정한다**

## 결정과 채택 근거
**3번.** 공통 통로(`app/integrations/http.py`)는 "못 받았다"는 사실만 예외로 올리고,
그게 치명적인지 아닌지는 `kakao.py`·`weather.py`가 각자 정한다.

1번과 2번이 틀린 이유는 같다 — **모든 외부 API를 똑같이 다루는 것 자체가 틀린 전제다.**
`blocks.place_id`는 `NOT NULL`이고 빈 문자열도 금지다(ADR-0009의 환각 차단 계약). 그 값을
만들 수 있는 곳이 카카오뿐이라, 카카오가 죽으면 만들 수 있는 일정이 없다. 반대로 날씨는
일정을 더 좋게 만드는 재료이지 존재 조건이 아니다. 같은 장애에 다르게 반응하는 것이 "장애
격리"의 실체다. 1번은 날씨 하나로 서비스를 멈추고, 2번은 장소를 못 찾았는데도 계획을 계속
진행시켜 place_id 없는 블록을 만들려다 DB CHECK에서 죽는다 — 진짜 원인에서 두 층 떨어진
곳에서.

### 딸린 결정 9개

**(1) 실패의 무게는 호출자가 정한다.**
`http.fetch_json`은 `UpstreamUnavailable`만 올린다. `kakao.search_places`는 그걸 그대로
통과시키고, `weather.get_daily_forecast`는 잡아서 `None`을 준다. **`None`은 에러가 아니라
"모른다"는 정상 응답**이고, 세션 12~14의 그래프는 그걸 정상 분기로 다룬다.

이 비대칭은 코드를 읽어서는 안 보인다. 그래서 `tests/test_integrations.py`에
`test_a_dead_upstream_is_fatal_for_places_but_not_for_weather`를 두어 **같은 장애를 한 화면에
놓고** 두 반응을 나란히 붙잡는다.

*뒤집는 조건*: 장소 출처가 둘 이상이 되면(카카오 실패 시 대체 검색) 카카오도 치명적이지
않게 된다. 그때 판단은 `kakao.py`가 아니라 그 위의 장소 해석 층으로 올라간다.

**(2) 재시도는 429와 5xx만. 그 외 4xx는 즉시 포기한다.**
401(키 오류)·400(잘못된 파라미터)은 다시 물어도 같은 답이다. 재시도하면 사용자 대기시간이
3배가 되고 쿼터도 3배로 탄다 — 아무것도 얻지 못하면서. 최대 3회 시도(재시도 2회), 백오프
0.2s→0.6s에 지터를 얹는다. 지터가 없으면 죽은 업스트림이 살아나는 순간 밀린 요청이 한꺼번에
같은 리듬으로 다시 밟는다.

3회로 정한 근거는 예산이다. 타임아웃이 connect 2s / read 3s이므로 최악 소요가 약 16초이고
실측으로는 10초 안쪽이다(전송 실패 시 1.0초, 실측). 4회로 늘리면 대기가 선형으로 늘지만
살아날 확률은 거의 안 는다. 사람이 기다리는 시간이라 LLM(수십 초)과 같은 예산을 줄 수 없다 (R1).

**(3) tenacity를 넣지 않는다.**
"무엇을 재시도하고 무엇을 안 하는가"가 이 세션의 결정 자체인데, 라이브러리에 넣으면 그
결정이 데코레이터 인자로 숨는다. 루프는 20줄이고 읽으면 정책이 보인다 (R3).

**(4) 캐시는 성공만 저장한다.**
실패를 캐시하면 업스트림이 살아난 뒤에도 TTL이 끝날 때까지 **우리 쪽에서 장애를 연장한다.**
장애 시간이 업스트림의 다운타임이 아니라 우리 TTL로 결정되는 건 뒤집힌 그림이다.

**(5) 캐시 장애는 미스로 흡수한다. 단, RedisError만.**
Redis가 죽으면 `get_json`은 `None`, `set_json`은 조용히 통과한다 — 캐시는 있으면 빠르고
없으면 느릴 뿐이어야 한다. 소켓 타임아웃은 **0.2초**로 짧게 건다. 죽은 캐시를 기다리느라
요청이 늘어지면 캐시는 성능 개선이 아니라 장애 증폭기가 된다.

`Exception`이 아니라 `RedisError`만 삼킨다. JSON 디코드 실패는 업스트림 장애가 아니라
**우리가 저장한 값이 깨졌다**는 뜻이고, 조용히 미스로 처리하면 원인을 영영 못 찾는다.
`tests/test_cache.py::test_a_corrupt_cached_value_is_not_swallowed`가 이 경계를 붙잡는다.

이 결정은 `weather.py`가 `Exception`을 넓게 잡는 것과 모순처럼 보이는데, 다른 층이라 다르다.
캐시의 깨진 값은 **우리 버그**라 개발 중에 크게 터져야 하고, 날씨 응답 모양이 바뀌는 것은
**업스트림 변경**이라 새벽에 계획 생성을 멈추면 안 된다(운영 인력 0명 — R3). 대신 `logger.exception`
으로 크게 남긴다.

**(6) 날씨 캐시 키의 좌표는 소수 2자리로 반올림한다.**
이 한 줄이 그 캐시의 존재 이유다. 블록마다 좌표가 미세하게 다른데 그대로 키에 넣으면
적중률이 **구조적으로 0**이 된다 — 캐시가 있는데 한 번도 안 맞는 상태가 조용히 유지된다.
2자리는 약 1.1km이고 예보 모델의 격자 자체가 10km 단위라 잃는 정보가 없다.
물어보는 좌표도 같이 반올림한다 — 그래야 캐시에 든 값이 키가 가리키는 지점의 값이다.

수동 검증에서 100m 떨어진 두 좌표가 한 캐시 항목을 공유하는 것을 확인했다(키 1개, 1128ms → 1ms).

**(7) 예보 범위 밖은 부르지 않는다.**
Open-Meteo의 예보 상한은 16일이다. 석 달 뒤 여행에 예보가 없는 것은 장애가 아니라 정상이라,
안 될 걸 알면서 요청을 만들지 않고 `None`을 준다. 끝 날짜만 범위를 넘으면 잘라내고 앞부분을
돌려준다 — 4일 중 2일이라도 아는 것이 통째로 모르는 것보다 낫다.

**(8) 로깅을 도입한다. 표준 `logging`만, 그리고 인증값은 반드시 헤더로 보낸다.**
지금까지 `app/` 안에 로그가 0줄이었다. 그런데 장애 격리는 **조용히 실패하는 설계**라,
로그가 없으면 날씨가 죽은 걸 아무도 모른다 — 감시가 정체성인 서비스에서(R2) 이건 모순이다.
structlog/loguru는 넣지 않는다. uvicorn이 이미 로거를 설정해 두었다 (R3).

우리 로그에는 url·params·headers를 넣지 않는다. **그런데 그것만으로는 부족하다는 것을 수동
검증에서 확인했다 — httpx 자신의 INFO 로거가 매 요청마다 전체 URL을 쿼리스트링째로 찍는다.**
uvicorn 기본 레벨이 INFO라 배포 환경에서도 그대로 나온다. 그래서 진짜 불변식은 로거 설정이
아니라 **인증값은 반드시 `headers`로 보낸다**이다 — URL이 어디에 남아도 비밀이 아니게 만든다.
카카오는 `Authorization: KakaoAK ...` 헤더라 성립하고, Open-Meteo는 키가 없다.

*뒤집는 조건*: 쿼리스트링에 키를 요구하는 업스트림(기상청 `serviceKey`, OpenWeatherMap
`appid`)을 붙이는 순간 이 불변식이 깨진다. 그때는 URL 마스킹이 그 API보다 먼저다.

**(9) 테스트는 `httpx.MockTransport`로 한다. 목킹 라이브러리를 추가하지 않는다.**
이 리포에 목킹 선례가 없어 처음 정하는 규약이다. MockTransport는 새 의존성이 0이고(httpx는
이미 있다) **전송 계층에 끼우므로 재시도·타임아웃·파싱·캐시라는 진짜 코드 경로가 그대로
돈다** — 가짜인 것은 응답뿐이다. `search_places`를 통째로 목킹했다면 이 세션이 만든 것 중
검증되는 게 하나도 없다. respx는 같은 일을 하는데 의존성이 하나 는다.

전역 클라이언트 교체에는 pytest 내장 `monkeypatch`를 쓴다(역시 새 의존성 0). MockTransport
핸들러가 요청을 기록하게 해서 **"네트워크를 몇 번 탔는가"를 숫자 하나로** 만든다 — 재시도
횟수와 캐시 적중을 그 숫자로 판정한다.

캐시 테스트는 진짜 Redis를 쓴다(db 15). 이 프로젝트가 진짜 PostgreSQL을 쓰는 것과 같은
이유이고, 여기서는 더 절박하다 — 캐시는 장애를 미스로 흡수하도록 만들어져 있어서, **Redis가
없으면 "캐시 히트" 계약이 조용히 통과해 버린다.** 그래서 `redis_cache` 픽스처만은 접속을
명시적으로 확인하고 크게 실패한다.

### 설정 기본값: fail fast의 의도적 예외
`redis_url`과 `kakao_rest_api_key`에 기본값을 준다. `database_url`·`jwt_secret`이 기본값
없이 import 시점에 죽는 것과 어긋나지만, 근거가 있다 — **CD는 서버의 `.env`를 고치지 않는다.**
필수 필드로 만들면 이 커밋이 머지되는 순간 EC2의 앱이 import에서 죽고, 배포 검증이 그걸
잡더라도 이미 서비스는 내려간 뒤다. `git_sha`가 이미 같은 이유로 기본값을 갖는다.

카카오 키가 비어 있을 때의 실패는 `KakaoNotConfigured`로 **호출 지점에서** 난다. 키가 없다고
로그인·여행 조회까지 멈출 이유가 없다. 네트워크를 타기 전에 걸러서 헛되이 3번 재시도하지도 않는다.

`REDIS_URL`은 `DATABASE_URL`과 같은 규칙이다 — `.env`는 하이브리드 기준 `localhost`,
컨테이너 주소는 compose가 덮어쓴다(ADR-0005). prod 조립도는 DB와 달리 **redis 위치를 직접
정한다**. DB는 RDS일 수도 컨테이너일 수도 있어 조립도가 몰라야 하지만, redis는 그 조립도 안에
있어서 위치가 확정이다. 덕분에 서버 `.env`를 손대지 않아도 배포가 성립한다.

dev compose의 redis에 `6379:6379`를 열었다. 없으면 하이브리드 개발에서 캐시가 통째로 죽은
채 도는데, **장애 격리 덕분에 그 사실이 조용히 묻힌다** — 잘 만든 격리가 개발자를 속이는
경우라, 포트를 여는 것이 격리를 끄는 것보다 낫다.

### 구조: integrations는 도메인이 아니다
4파일 문법(router/service/models/schemas)을 따르지 않는다. 그건 **도메인 규칙**이고
(ADR-0008·ADR-0009), integrations는 ROADMAP 4장이 "외부 API 툴 레이어"로 따로 적어 둔 층이다.
의존 방향은 `도메인 → core/integrations` 단방향이라 이 층은 도메인을 모른다.

공통 호출부를 `core/`가 아니라 `integrations/http.py`에 둔 것은, 이걸 쓰는 것이 integrations
안의 모듈들뿐이기 때문이다. `cache.py`는 반대로 `core/`에 있다 — Phase 5의 Redis 락이
monitoring 도메인에서 같은 클라이언트를 쓰게 되고, ROADMAP 4장 트리도 `core/`에 적어 두었다.

## 뒤집는 조건
- 위 각 결정의 뒤집는 조건이 개별로 적혀 있다
- 외부 API가 셋을 넘고 모듈마다 캐시 키 규약이 갈리기 시작하면, `fetch_json`에 키 생성까지
  올린다. 지금은 각 모듈이 자기 키를 만드는 것이 읽기 쉽다
- Celery 워커(Phase 5)가 이 층을 부르게 되면 전역 싱글턴 클라이언트의 수명이 요청이 아니라
  워커 프로세스가 된다. 그때 `aclose()` 호출 지점을 lifespan 말고도 하나 더 만들어야 한다
